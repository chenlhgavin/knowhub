上一章我们把塞满目标的大提示拆成了链:一步一目标、角色分工、结构化交接,可靠性上了台阶。

链上线没几天,新问题来了。假设你用链搭了个客服智能体,专门处理「查订单」:解析订单号 → 查数据库 → 组织回复,跑得很稳。可用户不按剧本出牌——有人问「这款耳机防不防水」,有人说「连不上蓝牙怎么办」,还有人只丢下一句「你们也太慢了」。

这些请求被硬塞进同一条「查订单」流水线,结果可想而知:产品咨询被当成订单号去解析,投诉被回了句「未查询到订单」。问题不在链拆得不好,而在链天生只有一条路——它定义了「怎么走」,却回答不了「走哪条」。这正是《Agentic Design Patterns》第二个模式——路由(Routing)要补的课。

读完你会得到:

- 一个心智模型:路由 = 给智能体装一个分诊台;
- 一张选型表:LLM、Embedding、规则、ML 分类器四种路由机制的取舍;
- 一份判断清单:路由发生的三个时机,以及什么时候不该上路由。

## 从固定路线到分诊台

先给路由一个白话定义:在智能体的工作流里加入条件逻辑(Conditional Logic),让它先评估输入,再从多条可能的路径中选一条走,而不是永远执行同一条固定序列。

原书的客服例子,加上路由后是这样运转的:第一步先做意图识别——意图(Intent)指用户这句话背后想办的事;再按意图分发:「查订单」走订单数据库的链,「产品咨询」走产品目录检索的链,「技术支持」走排障指南或转人工,意图不明的走澄清链,反问一句再分。

![图1:固定链 vs 路由分诊](/knowhub/images/articles/routing-basics/blog-rt1-chain-vs-routing.png)

注意一个容易忽略的细节:分诊台后面接的,还是上一章那些链。路由不替代链,它站在链的上游,决定请求进哪条链。两个模式是分工关系:链负责把一类任务做稳,路由负责把请求送对地方。

这里还能看到上一章「结构化交接」的影子:分诊这一步的输出必须是机器可读的明确信号——一个类别标签,而不是一段自由发挥的分析。后续程序拿到标签才能精确分发;要是分诊员答一句「这位用户似乎想咨询产品」,分发逻辑就又得靠猜了。

为什么非加这一步不可?因为不加,你只剩两个坏选项:要么把所有分支逻辑塞回一个大提示,让模型「看情况自己发挥」——那正是上一章刚逃离的火坑;要么给每类请求单独开一个入口,让用户自己选——体验倒退十年。

**链解决「怎么走」,路由解决「走哪条」;分诊台一立,智能体才接得住真实世界的活。**

## 四种路由机制,各自什么脾气

分诊台立起来了,谁来当分诊员?原书给出四种实现机制。

LLM 路由:直接让语言模型当分诊员——提示它「分析以下请求,只输出类别:订单 / 产品 / 支持 / 其他」,系统读这个词决定分发。最灵活,再刁钻的表达也能理解;代价是每次分诊多一次模型调用,延迟和费用都涨,输出还偶有不听话。

Embedding 路由:向量嵌入(Embedding)是把文字变成一串数字向量,语义越近的文字向量越相似。把请求转成向量,和每条路线的代表向量比相似度,谁近走谁。按语义而非关键词匹配,适合「同一个意思有一百种问法」的场景——「想退货」「这单不想要了」「钱怎么退」一个关键词都不重合,向量却都落在「售后」附近。

规则路由:if-else、关键词、正则表达式。最快、零成本、结果完全确定;但撞上没预料过的表达就抓瞎,规则也会越堆越多、越来越难维护。

ML 分类器路由:用标注数据微调一个小分类模型,专职分诊。它和 Embedding 路由一样不靠生成式模型现场推理,但多了监督训练这道工序,分得更准更稳;代价是要先攒标注数据。原书还点了一个细节:LLM 可以在训练前帮忙合成标注数据,但真正做分诊决定的那一刻,它不在场。

![图2:四种路由机制对比](/knowhub/images/articles/routing-basics/blog-rt1-four-mechanisms.png)

怎么选?一条实用的默认路径:类别边界清楚、表达方式有限,先用规则,便宜又稳;表达千变万化、类别需要「理解」才能分清,上 LLM 或 Embedding;请求量大到在乎每次分诊的延迟费用、又攒得出标注数据,再考虑训练专职分类器。

**分诊员没有最优解:规则买确定,LLM 买灵活,分类器用训练成本换运行时的又快又准。**

## 路由不只发生在入口

提到路由,多数人脑中都是刚才那个画面:请求一进门就分诊。但原书强调,路由可以发生在智能体操作周期的多个节点上,典型的有三个时机。

时机一,入口分类:请求刚到就判定主任务类型,决定进哪条链——前面客服例子就是。

时机二,链的中间:上一步的输出决定下一步走哪条支线。文档处理链跑到一半,发现这批数据是 JSON 而不是 CSV,后续要换解析支线;抽取出的发票金额超过阈值,转人工复核。上一章用例篇讲过的发票校验回路,「校验不通过就退回重试」,本质就是一次链中路由。

时机三,子流程里选工具:同一个「查资料」动作,面前摆着搜索引擎、内部知识库、计算器三件工具,挑哪件本身就是一次路由决策。

![图3:路由的三个时机](/knowhub/images/articles/routing-basics/blog-rt1-three-junctures.png)

三个时机叠起来,智能体的执行图就从一条直线长成一棵树:入口分大类,链中按状态转向,末端挑工具,每个分叉点都是一次小分诊。

顺带补一句工程背景:LangGraph 这类框架把工作流显式建模成状态图(State Graph)——节点是步骤、边是转移条件,天然适合表达这种多节点路由,下一篇会展开。

**路由是分叉点,不是门卫:入口、链中、选工具,哪里有选择,哪里就有路由。**

## 什么时候该上路由

原书的实践建议(Rule of Thumb)一句话:当智能体必须根据输入或当前状态,在多个互不相同的工作流、工具或子代理之间做选择时,用路由。典型如需要分诊、分类的入口场景:客服机器人分辨售前咨询、技术支持、账号管理。

反过来,两种情况别上路由。其一,请求类型单一、流程确定,一条链从头走到尾,加路由纯属多一次调用、多一个故障点。其二,类别之间的界限模糊到人都分不清——这时路由只会把「分错」做得更自动化,先回去把类别设计清楚再说。

还有一个常被漏掉的设计:永远给分诊台留一条「意图不明」的出口。真实流量里总有分不进任何类别的请求,与其硬塞进最接近的类,不如走澄清链反问一句。这条兜底路线的具体做法,下一篇的两个框架实现里都会见到。

![图4:该不该上路由的判断](/knowhub/images/articles/routing-basics/blog-rt1-when-to-route.png)

**判断只需一句:请求需要「分」才处理得好,就上路由;不需要分,就让链安静直行。**

## 写在最后

三条 takeaway:

- 路由给智能体装上条件逻辑,从固定路线升级为动态选路;链管怎么走,路由管走哪条;
- 四种分诊员各有账本:规则买确定,LLM 和 Embedding 买灵活,ML 分类器用训练成本换运行时性价比;
- 路由可以出现在入口、链中、选工具三个时机,哪里有选择,哪里就有分叉。

边界也说清楚:路由不是免费的——LLM 分诊每次多一跳调用,延迟费用同步上涨;分诊员会分错,错分的请求会进错链,所以兜底出口必须留;而如果类别本身没设计清楚,换哪种机制都救不了。

下一篇进实战:同一个「预订 + 咨询」场景,LangChain 和 Google ADK 给出两条完全不同的实现路——一条让你亲手把分支画在明处,一条让你把分支交给模型。两种范式怎么选,下篇见。
