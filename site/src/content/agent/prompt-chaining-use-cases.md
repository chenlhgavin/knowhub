做发票自动化的同学大概都试过:把一张发票图片丢给模型,「把姓名、地址、金额都抽出来」。十张里八张没问题,剩下两张——金额漏了,或者日期格式五花八门。

你加上一句「务必抽全所有字段」,好了一点:两张翻车变成一张半。但无论怎么改措辞,始终到不了能上生产的稳定度。

上一篇《一个大提示,不如一条链》讲了提示链(Prompt Chaining)的原理:拆步骤、指派角色、结构化交接。这一篇看落地:原书第一章给了七类典型场景,我们把拆法画出来,并回答一个更实际的问题——你手上的任务,到底该不该拆?

读完你会得到:

- 一张七类场景的「拆链地图」;
- 两个深挖案例:带校验回路的数据抽取链,并行 + 串行的研究智能体;
- 四条「该不该拆」的经验法则。

## 七类场景,一张地图

原书列了七个用例。逐个背没有必要,按「链在替你解决什么」归成三组,记忆负担小得多:

![图1:提示链的七类落地场景地图](/knowhub/images/articles/prompt-chaining-use-cases/blog-pc2-seven-scenarios.png)

数据变形类,链在把信息一步步「变干净」:信息加工流水线(提取、总结、抽实体、查知识库、出报告),数据抽取与转换(抽取、校验、修正、规范化),多模态推理(先读图中文字,再关联标签,最后按表格解读)。

多步推理类,链在替你把思考过程摊开:复杂问答先拆子问题、逐个检索再综合;代码生成从伪代码到初稿、查错、重写、补文档,一步一个台阶。

上下文累积类,链在维持连续性:内容生成从选题、大纲到逐节起草、整体修订;多轮对话则把每一轮都构造成新链——识别意图、更新状态、生成回应,历史滚动累积。

这三组对应的产品形态也很典型:数据变形类常见于文档自动化场景,多步推理类支撑研究助手和编程助手,上下文累积类则是客服机器人和写作工具的底座。

拿到新需求,先在图里找同类:解析发票、表单、合同的,对号数据变形类;要查资料、做判断、给结论的,对号多步推理类;产出长内容或多轮交互的,对号上下文累积类。找到同类,拆法直接抄。

**场景千变万化,拆法只有一个:让每一步只回答一个问题。**

## 深挖一:数据抽取链,把「靠运气」变成「有抓手」

回到开头的发票问题。原书把它归为数据抽取与转换类:把非结构化文本变成可靠的结构化数据,是提示链最高频的落地场景之一。

单提示抽取的死穴在于:缺了字段你无从定位,更没有重试的抓手。原书给出的拆法,核心是在链里加一个校验回路:

![图2:数据抽取链的校验回路与外部工具](/knowhub/images/articles/prompt-chaining-use-cases/blog-pc2-invoice-loop.png)

第一步照常抽取;第二步交给程序校验——字段齐不齐、格式对不对。这一步是确定性代码:规则可测试、结果可复现,比让模型「自己检查自己」可靠得多。

校验不通过,才触发第三步。注意它的细节:不是把原任务重跑一遍,而是定向补抽——只针对缺的字段,并附上「上一轮哪里失败」的上下文。重试因此更便宜,也更容易命中。实践中还要给循环设上限:两三轮仍不过就转人工,别让链空转(这一条是工程经验,原书未展开)。

后面两步同样值得注意:规范化把「一千零五十」这样的文本转成数值 1050;而金额加总这种精确计算,原书明确建议交给外部计算器工具——大语言模型做算术并不可靠。

这个分工原则可以推广:模型擅长理解和转换,不擅长精确执行。凡是有确定答案的操作——算术、查表、格式校验——都交给代码或工具,把模型留给真正需要语义理解的环节。

整条链跑完,交付的不是「模型觉得对」的结果,而是「校验规则说对」的结果——这两句话的差别,就是能不能上生产的差别。

**链的中间可以插入确定性代码——校验、分支、重试,都不靠模型自觉。**

## 深挖二:研究智能体,并行与串行各干各的

第二个深挖对象是自动研究智能体:给一个主题,产出一份综合报告。原书用它说明一个容易被忽略的点:不是所有步骤都该串行。

![图3:研究智能体的并行采集与串行综合](/knowhub/images/articles/prompt-chaining-use-cases/blog-pc2-research-agent.png)

检索回来的 N 篇文章,逐篇抽取要点时互不依赖——这段应该并行跑,快 N 倍。但从「汇总」开始,流程变成严格串行:先合并全部要点,再综合成稿,最后审校修订,每一步都以上一步的完成为前提。

判断一段流程能不能并行,只看一个问题:子任务之间有没有数据依赖。文章 A 的抽取结果不影响文章 B,并行安全;综合成稿必须等全部要点到齐,这是硬依赖,只能排队。

提示链管的是后半段:汇总结果作为综合提示的输入,综合稿再作为审校提示的输入。前半段的并行,则是编排框架(如 LangGraph)的事。真实系统里,这种「并行采集 + 串行综合」的混合工作流是常态,而不是特例。

顺序也有讲究:审校放在最后单独一步,而不是让综合步骤「顺便检查」——理由和第一篇说的一样,一步只做一件事,审校才审得出问题。

**能并行的别排队,有依赖的才上链。**

## 该不该拆?四条经验法则

看完场景,回到你自己的任务。原书的 Rule of Thumb(经验法则)给了四条判断标准,满足任意一条,就值得拆链:

![图4:什么时候该用提示链的四条经验法则](/knowhub/images/articles/prompt-chaining-use-cases/blog-pc2-rule-of-thumb.png)

一是任务复杂到单个提示装不下,多个目标互相干扰;二是流程有多个明显阶段,比如总结、分析、成稿天然分步;三是步骤之间需要调用外部工具,查库、算数、调接口;四是要构建多步推理、需要维持状态的智能体系统。

第四条尤其常见:凡是「智能体」类产品——会规划、会调工具、会记住上下文——它的每一次行动背后,几乎都藏着一条链。

四个信号也对应四种收益:拆掉复杂度换稳定,拆出阶段换可调试,拆开步骤换工具接入,拆出状态换连续性。你最想要哪个收益,决定了链该怎么设计。

反过来也成立:三句话能说清的单一任务,直接一个提示解决。成本要算清楚——一条五步链就是五次调用,延迟和费用大致翻五倍。在线场景常见的折中,是把强依赖的关键步骤拆开,把轻量步骤合回一个提示:链的粒度,本身就是设计决策。

**多阶段、要验证、要工具、要状态——见到这四个信号,就该拆链。**

## 写在最后

三条 takeaway:

- 七类场景共用一个套路:拆步骤,让每步只回答一个问题;
- 链的强大之处在步骤之间:校验代码、条件分支、外部工具都插在这里;
- 拆不拆看四个信号:多阶段、要验证、要工具、要状态。

配合上一篇的三板斧(拆步骤、指派角色、结构化交接),本篇的校验回路和并行分段,就是工具箱里的第四、第五件武器。

边界与局限:线性链不是万能的。复杂的状态管理和动态分支需要图结构(LangGraph 这类框架的主场);真正的多轮对话状态管理,也比逐轮拼接历史复杂得多;并行部分本身不属于链,它是编排的另一半。

另外,七个用例是「常见」不是「全部」:只要流程里能画出「上一步产出喂给下一步」的箭头,就是链的地盘。

下一篇是本系列的收官:当你把链拆好、每步的提示也调无可调,输出还是不理想——问题多半出在模型「看到的世界」上。我们讲上下文工程(Context Engineering):决定输出质量的四层信息结构。
