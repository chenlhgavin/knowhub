你大概也写过这样的提示词:「读一下这份市场研究报告,总结核心发现,找出三个最重要的趋势和支撑数据,再帮我起草一封发给市场团队的邮件。」一次讲清所有要求,看起来干净利落。

结果呢?总结写得像模像样,趋势数据却张冠李戴,邮件里的结论甚至和报告方向相反。你把提示词改了一遍又一遍——加编号、加粗、写「务必逐条完成」——它还是时不时漏掉某条要求。

问题多半不在措辞,而在结构:你让模型在一次调用里同时对齐了太多目标。本文要讲的提示链(Prompt Chaining),是《Agentic Design Patterns》全书的第一个设计模式,专治这种不稳定。

读完你会得到:

- 一张失败地图:大提示的五种典型翻车方式;
- 一套改造方法:拆步骤、指派角色、用结构化格式交接;
- 一条最小可用的两步链,以及需要升级框架时怎么选。

## 一次调用塞太多目标,模型会怎么翻车

先给「认知负荷」(Cognitive Load)一个白话定义:一次调用里,模型需要同时惦记的目标和约束越多,分给每一项的注意力就越少。

原书把大提示的典型故障归成五类,对应下图:指令忽略、上下文漂移、错误传播、窗口不足、幻觉。

![图1:一个大提示的五种失败模式](/knowhub/images/articles/prompt-chaining-basics/blog-pc1-five-failures.png)

指令忽略最常见:五条要求只完成三条。上下文漂移是写着写着忘了最初的设定和约束。错误传播最隐蔽——第一段总结错了一个数,后面的推理全部建立在这个错数上。

再加上关键信息在长上下文里「装不下、够不着」,以及负荷升高后编造内容的幻觉,一个大提示等于同时买了五张「事故彩票」,哪张开奖都够你查半天。

这五种失败还会互相放大:注意力被多个目标摊薄,既容易漏掉指令,也更容易在信息不足时用幻觉补位。原书的结论很直接:任务的多面性越强,单一提示的输出就越不可靠。

你可能会想:那把提示写得更详细呢?经验是,超过某个复杂度之后,往提示里加的每一条新约束,都在稀释其他约束被遵守的概率——这是结构问题,靠措辞解决不了。

**大提示翻车的根源不是措辞不好,而是一次调用里塞了太多目标。**

## 拆链:一次只让模型做一件事

提示链的思路就是分而治之:把大任务拆成一串小步骤,每步一个提示、只盯一个目标;上一步的输出,作为下一步的输入。步骤之间由此形成一条依赖链(Dependency Chain),「链」的名字正来自于此。

依赖链的另一面是「递进」:模型在每一步都基于前面已经确认的成果继续构建,理解逐步加深,而不是每次都从零面对整个问题——就像解题先列已知条件,再一步步推导。

开头那个翻车任务,拆成三步就顺了:

![图2:市场报告任务的三步链改造](/knowhub/images/articles/prompt-chaining-basics/blog-pc1-three-step-chain.png)

第一步只做总结,模型的全部注意力都放在「提炼核心发现」上;第二步基于已经检查过的总结提取趋势和数据;第三步拿着结构化的趋势清单写邮件。

原书还建议给每一步指派不同角色(Role):市场分析师做总结,行业分析师找趋势,专业文档撰写人写邮件。角色让每步的行为边界更清楚,输出口径更稳定。

为什么这样就稳了?三个原因:每步目标单一,歧义最小;哪步出错改哪步,不用推倒整个大提示重调;上一步的输出确认无误后才进入下一步,错误不会一路带到终点。

对比一下调试体验:大提示出错,你只能整体重跑、盲改措辞;链出错,你看一眼中间产物就知道断在哪一环。中间结果全程可见,是链最被低估的好处。

这条链还有一个隐藏收益:每两步之间都是一个天然「接口」,可以插入外部动作——查数据库、调 API、跑一段校验代码。链因此不只是提示的串联,而是模型与工具协同的工作流,这也是原书称它为智能体系统地基的原因。

**可靠性来自每一步的专注,而不是提示的长度。**

## 步骤之间传什么:结构化输出

链拆好了,还剩一个决定成败的细节:上下游怎么交接。

如果上一步输出的是一段自由发挥的自然语言,下一步就得靠「猜」来解析——趋势名是哪几个字?数据是 73% 还是「大约七成」?一次猜错,整条链跟着崩。

解法是让关键步骤输出结构化格式,例如 JSON(键值对文本格式,程序可精确解析)或 XML:

![图3:自然语言交接与 JSON 结构化交接的对比](/knowhub/images/articles/prompt-chaining-basics/blog-pc1-structured-output.png)

字段名固定、取值明确,下一步可以把数据精确插进自己的提示里,不再依赖语义猜测。原书特别强调:链的可靠性高度依赖步骤之间传递数据的完整性,格式约束正是为此服务。

结构化交接还有一个附带好处:错误在交接处就地暴露。JSON 解析失败是一个明确、可编程处理的信号,能立刻重试或修正;自然语言里的解析错误则悄无声息,往往流到终点才被发现。

也不是每一步都要 JSON:面向人的最终输出(邮件、文章)保持自然语言;面向下一步提示的中间数据,才需要结构化。判断标准只有一条——这份输出的消费者是人,还是程序。

顺带一提,不少模型服务已提供强制 JSON 输出的接口选项,把格式约束从「提示里请求」升级成「接口上保证」,交接会更稳(具体能力以你所用服务的文档为准)。

**链的可靠性,等于最弱那一次数据交接的可靠性。**

## 最小可用的链:两步就够

原书的入门示例只有两步,却已经是一条完整的数据处理管道:第一步从一段产品描述里只抽取技术规格;第二步把规格转成固定字段(cpu、memory、storage)的 JSON。

![图4:最小两步链的数据流与框架选择](/knowhub/images/articles/prompt-chaining-basics/blog-pc1-minimal-chain.png)

注意中间那份「规格清单」:它是第一步的全部产出,也是第二步的全部输入。两步各自简单到几乎不会出错,而「抽取 + 格式化」混在一个提示里时,两个目标就会互相干扰。

图 4 还藏着一个设计要点:两个提示的分工是「理解」与「映射」。第一步做语义工作——判断哪些词是技术规格;第二步几乎是机械转换——把干净的规格填进固定字段。难度被前移并隔离,越往后的步骤越「笨」,也越稳。

工程上,这类链不需要你手写胶水代码搬运输出。LangChain 的表达式语言 LCEL 用管道符把「提示 → 模型 → 输出解析器」串成链,上一步输出自动填进下一步提示的槽位。

两个实践细节值得记下。其一,原书示例把温度(temperature,控制输出随机性的参数)设为 0——抽取、格式化这类步骤要的是确定,不是创意。

其二,框架有分工:LangChain 适合线性序列;当链需要分支、循环和状态管理时,升级到 LangGraph,或 CrewAI、Google Agent Development Kit(ADK)这类多智能体编排框架。

**先跑通一条两步链,再谈复杂智能体。**

## 写在最后

三条 takeaway:

- 大提示不稳的根源是目标过载,五种失败模式都由此而来;
- 拆链三板斧:一步一个目标、每步指派角色、步骤间用 JSON 等结构化格式交接;
- 提示链是多步智能体系统的地基,后续所有编排模式都建在它上面。

边界也要说清楚:链不是免费的。每多一步就多一次模型调用,延迟和费用同步上升;链也不消灭错误,只是把错误关进更小、更容易定位的格子里;三句话能说清的简单任务,拆链纯属过度设计。
