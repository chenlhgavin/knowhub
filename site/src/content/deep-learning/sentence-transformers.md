上一篇[《一文读懂 BERT》](/knowhub/topics/deep-learning/bert-family)的结尾留了个尾巴：BERT 理解句子很强，但直接拿它的输出当"句子向量"，在语义相似度任务上表现意外地差——甚至不如 GloVe 词向量取平均。

偏偏"把整句话变成一个向量"是需求最大的场景之一：语义搜索要找和当前问题最像的历史工单；去重聚类要知道 100 万条评论里有几种意见；RAG（Retrieval-Augmented Generation，检索增强生成）要为用户提问找出最相关的文档片段。这些任务的基本单位都是**整句话/整段话**，且都指向同一个要求：**语义相近的句子，向量也要相近**（余弦相似度高）。

2019 年的 Sentence-BERT（SBERT，后来发展成 `sentence-transformers` 库）补上了这块拼图。它的答案可以压成一句话：**双塔结构把"比较"挪出模型，对比学习把"语义相近"压进向量**。

本文由浅入深：先看两个想当然的方案为什么不行（第一节），再拆 SBERT 的双塔结构与池化（二、三节），然后是训练的灵魂——对比学习（第四节），最后是工程标准答案 retrieve & re-rank、三行代码上手与局限（五、六、七节）。

---

## 一、两个想当然的方案，为什么都不行

> 本节回答：BERT 明明已经很懂句子了，句向量为什么还要专门做？

**方案 A：直接拿 BERT 的 `T<cls>`，或把词向量取平均。** 质量差。原因不玄：BERT 预训练时**没有任何目标要求它把"句子语义相似度"编码进单个向量**——MLM 学的是词，NSP 只学"两句是否相邻"。不是 BERT 不懂句子，而是它的懂法没有被"压"进一个向量里。

**方案 B：把两句拼接起来一起过 BERT（cross-encoder）。** 上一篇讲过的句对任务正是这个结构：`<cls> 句A <sep> 句B` 拼成一条序列，12 层注意力充分交互后由 `T<cls>` 出一个相似度分——**精度很高**。但它每比较一对，就要完整跑一遍模型：

![cross-encoder 的账单：组合爆炸且无法复用](/knowhub/images/articles/sentence-transformers/blog-sbert-cost.png)

左边是账单：1 万个句子互找最像，要比 C(10000, 2) ≈ **5000 万对**，就是 5000 万次 BERT 前向、数十小时。而且这是**纯推理成本**——模型早已训练好，全程只有前向计算；这笔账每次执行任务都要重付，库里新增一句还得为它重算一轮配对。

右边是症结：这数十小时**换不来任何可复用的东西**。拼接输入后，自注意力从第 1 层就把两句搅在一起——句B 是"手机发布会"，句A 里"苹果"的中间表示偏向公司；句B 换成"果园丰收"，就偏向水果。模型算出的一切都是这一**对**的函数，内部根本不存在"句A 自己的表示"这种可缓存的中间结果，换个比较对象只能从头重跑。

值得停一秒品味：**cross-encoder 准的原因（两句从底层充分交互）和慢的原因（表示与比较对象深度耦合、无法缓存）是同一件事。** 想要可复用，就得把两句解耦——这就是双塔。

## 二、SBERT 双塔：把"比较"挪出模型

> 本节回答：怎么让每句话只编码一次、向量随便比？

Sentence-BERT 的解法：两句**各自独立**过同一个 BERT（bi-encoder，双塔，共享权重），各自池化成一个定长向量（如 384/768 维），"比较"退化成模型**外**的一次余弦计算（纳秒级）：

![SBERT 完整网络结构](/knowhub/images/articles/sentence-transformers/sbert-architecture.png)

- **左图（SBERT 双塔）**：自下而上 = 两句各自进塔 → 三嵌入相加（与 BERT 完全同款；单句输入没有"第二句"，段嵌入退化成常数）→ 同一个 BERT → 每词元输出向量 → mean pooling 压成句向量 u/v（第三节）→ 余弦相似度。注意"语义近→向量近"不是结构自带的，要靠对比学习训出来（第四节）。
- **右图（cross-encoder 对照）**：两句拼一条序列充分交互——准，但没有可复用的向量。

账单立刻翻转：1 万句互找最像 = **1 万次编码（一次性）+ 5000 万次向量点积（秒级）**；新句子来了只需编码 1 次，配合向量索引（FAISS 等）毫秒级检索。

> 本质是**把算力从"查询时"搬到"建库时"**：编码结果存进向量数据库反复使用——这正是 RAG 检索的地基。cross-encoder 按"对数"付模型调用费（O(N²)），双塔按"句数"付（O(N)）。

## 三、池化：N 个词向量压成 1 个句向量

> 本节回答：BERT 输出的是每词元一个向量，怎么变成一句一个？

这一步叫**池化（pooling）**。SBERT 默认、也最稳的是 **mean pooling**：把 N 个词元的输出向量摞成一张 N×768 的表，**按列压扁**——句向量的第 k 维 = N 个词元第 k 维的平均值：

![mean pooling：按列压扁](/knowhub/images/articles/sentence-transformers/blog-sbert-pooling.png)

输出恒为 1×768、与句长 N 无关——"定长句向量"正是这么来的。最容易搞反的是方向：不是把每个词元自己的 768 维平均成一个数（那样得到 N 个数、维度信息全丢），而是**同一维上 N 个值互相平均、768 个维度各算各的**。

> 似曾相识？CBOW 把上下文词向量"先平均"就是同款操作。区别在于这里被平均的是**上下文相关**的 BERT 输出，且后面还有专门训练兜底，所以效果远好于平均静态词向量。

## 四、对比学习：正例拉近、负例推远

> 本节回答：光改结构就够了吗？"语义近 → 向量近"是从哪来的？

不够——不训练的双塔就是方案 A 的质量。SBERT 的训练思想一句话：**让相似句对的向量互相靠近，不相似句对的互相推远**。这和 word2vec 负采样是同一个哲学，只是单位从"词对"变成了"句对"。正例数据现成的：自然语言推断（NLI）里的"蕴含"句对、问答对、翻译句对、用户点击日志……

负例更妙——**根本不用造**。最常用的损失 MultipleNegativesRankingLoss（批内负采样，in-batch negatives）：一个 batch 里有 N 个正例句对，对每个句子来说，自己的搭档是正例，batch 里其他所有句子全是白捡的负例：

![批内负采样：对角线拉近、其余推远](/knowhub/images/articles/sentence-transformers/blog-sbert-contrastive.png)

以 batch = 3 走一遍：三对正例（怎么退货↔退货流程是什么、小猫在睡觉↔一只猫睡着了、如何开发票↔发票怎么开），6 句各自过双塔得到 u/v，两两算余弦得 3×3 矩阵——**对角线是正例，其余格是批内负例**。每行做一道"3 选 1"：相似度放大后按行 softmax，损失 = −log P(对角线)。

图里第 3 行是精华：训练初期，"如何开发票"竟觉得"退货流程是什么"（0.61）比自己的正例"发票怎么开"（0.57）还像——售后客服同款句式，天然的**难负例**——于是这行被重罚（损失 1.24），梯度狠推 u₃↔v₁、轻推 u₃↔v₂，**力度与"抢走的概率"成正比**。训练成熟后，矩阵变成对角线明显高于其余："语义近 → 向量近"就这样被一步步压进向量。

两个实现细节，点到为止：

- **缩放系数 ×20**：余弦被压在 [−1, 1]，候选间分差只有零点几，直接 softmax 概率接近抽签——连答对了都拿不到高分（正例 0.9 对负例 0.1 的压倒性区分，softmax 后正例概率也只有 0.53、损失降不下去）。先 ×20 放大分差，指数函数才拉得开概率，损失和梯度才恢复"按错定价"。
- **batch 越大越好**：batch = 64 时每个句子免费得到 63 个负例，"选对"越难，被迫学出的区分度越强。

> 对照 BERT 的 MLM（考点位置算 −log P(答案)）：同一个交叉熵配方，"词表"换成了 batch 内的候选句——**从"猜词"换成了"认句"**。

## 五、精度召回兼得：retrieve & re-rank

> 本节回答：双塔快但略糙、cross-encoder 准但太慢，工程上怎么选？

不选，都要。双塔的精度略逊有结构性原因——两句编码时互相看不见，词级的精细对照做不了；cross-encoder 准，但只付得起小规模的账。工程标准答案是**两级流水线**：

![retrieve & re-rank 两级流水线](/knowhub/images/articles/sentence-transformers/blog-sbert-rerank.png)

100 万文档先离线编码入向量库；查询来了，① bi-encoder + 向量索引毫秒级召回 top-100，② cross-encoder 只对这 100 个候选逐对精排出 top-10。粗筛用快的、精排用准的——各取所长。RAG 系统里的 "retriever + reranker" 正是这套架构。

## 六、三行代码上手

> 本节回答：想用起来，从哪开始？

```python
from sentence_transformers import SentenceTransformer
model = SentenceTransformer("all-MiniLM-L6-v2")     # 384 维、22M 参数的经典小模型
emb = model.encode(["小猫在睡觉", "一只猫睡着了", "股市今天大涨"])
# emb.shape = (3, 384)；前两句余弦相似度高、和第三句低
```

模型怎么挑（截至 2026 年的常见选择）：

| 需求 | 常见选择 |
|---|---|
| 英文、轻量快速 | all-MiniLM-L6-v2（老经典） |
| 多语言/中英混合 | BGE-M3、multilingual-e5 系 |
| 中文 | BGE 系（bge-large-zh 等） |
| 榜单参考 | **MTEB**（海量嵌入基准，Hugging Face 排行榜） |

典型应用：语义搜索、RAG 检索、聚类与去重、语义缓存（相似问题直接复用答案）、少样本分类（向量 + 最近邻）。

## 七、局限与去向

> 本节回答：sentence-transformers 做不好什么？接下来往哪走？

**领域鸿沟**：通用模型到了专业领域（法律/医疗/代码）效果打折，需要领域数据微调。

**长文档**：多数模型有效长度几百 token，长文要**切块（chunking）**再各自编码。"有效几百"是三层限制叠出来的：位置嵌入只训了 512 个位置，超长直接截断（硬上限）；训练数据多是短句，标称 512 里靠后的位置没怎么练过（标称 ≠ 有效）；最根本的是**单向量容量**——就算塞得进，mean pooling 把几千词平均进一个向量，多主题长文会被稀释成"什么都沾一点、什么都不像"的糊状均值。所以切块不只是绕开上限，更是保住向量的区分度：每块主题单一、语义完整——切太碎上下文断裂、切太大向量发糊，"块怎么切"因此成了 RAG 的一门手艺。

**要自己管模型**：下载、部署、GPU、扩容……如果不想管这些，就把"文本进、向量出"外包给云端——这是 LLM Embedding API 的主题，留给下一篇。

> **一句话收尾**：sentence-transformers 用双塔把"比较"移出模型（一次编码、随便比），用对比学习把"语义相近"压进向量（正例拉近、负例推远——word2vec 的老哲学在句子级的重演）；配上 retrieve & re-rank，它是今天几乎所有语义检索和 RAG 系统的地基。
